# Changelog Policy

`CHANGELOG.md` is the human-readable history of meaningful changes: what changed, in
which version, when it was released, who or which platforms are affected, and whether
compatibility, security, privacy, data integrity or scientific reproducibility are
affected. It is not a copy of Git history or a work log.

## 1. Convention and structure

- Follow the repository's existing convention. For new changelogs use
  [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and
  [Semantic Versioning](https://semver.org/) when the project follows SemVer.
- Keep a changelog when the project has a meaningful version or release history; not
  every experimental repository needs one.

```markdown
# Changelog

All notable changes to this project are documented here.

## [Unreleased]

### Added
- Description of a completed but unreleased feature.

## [1.2.0] - YYYY-MM-DD

### Fixed
- Description of a resolved defect.
```

(Versions and dates above are placeholders.) Newest version first; `Unreleased` on top;
`YYYY-MM-DD` dates that are verified; no empty categories; no duplicates; consistent
headings; no decoration.

## 2. Categories

Added (new functionality) · Changed (existing behaviour) · Deprecated (still available,
scheduled for removal) · Removed · Fixed · Security (security changes appropriate for
disclosure). Add other categories only for a justified, recurring need.

## 3. Versions and release status

- Never invent versions or dates. A commit is not a release; the latest tag is not
  necessarily the latest stable release; a version number alone does not prove stability.
- Verify against version metadata, tags, GitHub Releases (including the prerelease flag),
  artifacts, release workflows and existing history. Report conflicts; never invent a
  heading to hide one.
- Distinguish development, alpha, beta, release candidate, stable and maintenance
  releases, and archived projects.

## 4. Unreleased work and releases

Completed, meaningful changes go under `Unreleased`; plans and incomplete work do not.
When preparing a release, move only the changes actually included, confirm the version,
tests, builds and platforms, keep unrelated unreleased entries, and set the date only when
the publication date is known. Preparing a changelog is not publishing: tags and releases
need the maintainer's decision.

## 5. Public and private repositories

Private repositories may keep internal release history without public links. Public
changelogs use publicly reachable links only and no internal paths, usernames or hosts.
Before a repository becomes public, review the changelog for confidential details,
personal paths, internal infrastructure, private links, sensitive research information,
undisclosed vulnerabilities and wrong release claims - and remember that history keeps
what the current file no longer shows. After a repository becomes private, keep accurate
history unchanged.

## 6. Platform-specific changes

Prefix entries with the platform (`**Windows:** ...`, `**Linux:** ...`) when availability
or behaviour differs; do not repeat platforms for general changes. Never claim platforms,
installers or packages that were not verified; separate "builds from source" from
"packages published". With independent platform version histories, state the platform
package version with platform-specific entries ([VERSION_MANAGEMENT](../VERSION_MANAGEMENT.md)).

## 7. Breaking changes

State compatibility changes prominently (formats, schemas, removed options, APIs, dropped
platforms, configuration, data migration, storage locations), using a GitHub alert when a
significant warning is justified:

```markdown
> [!IMPORTANT]
> This release changes the application database format.
> Back up existing data before upgrading.
```

Mention backups or migrations only when the implementation requires them, and link an
existing migration guide when there is one.

## 8. Security, privacy, scientific, performance and dependency changes

- **Security:** record meaningful fixes without exploit details, credentials or internal
  infrastructure; claim a fix only with evidence; follow the disclosure process; link
  advisories only when they exist.
- **Privacy:** record changes to data collection, telemetry, network use, crash reports,
  storage, cloud services, consent, retention, export and deletion; do not call software
  fully offline if it has optional network features.
- **Scientific software:** separate implementation changes from changes that can alter
  results; when a verified correction can change earlier results, say so (for example,
  "Results generated by affected versions may require reanalysis"); never claim earlier
  results are unaffected without validation.
- **Performance:** only evidence-based improvements; no invented numbers; give conditions
  for quantitative claims.
- **Dependencies:** only updates with impact on security, behaviour, installation,
  compatibility, licensing, packaging or reproducibility; never invent versions or
  vulnerability identifiers.

## 9. Presentation and links

Mostly text: version headings, consistent categories, concise bullets, important alerts.
No per-release logos, emoji, badge walls, galleries or graphs without real data. Link to
releases, tags, comparisons, issues, migration guides and advisories only when they exist;
relative links for repository documents; comparison links at the end of the file:

```markdown
[Unreleased]: https://github.com/<owner>/<repo>/compare/v1.2.0...HEAD
[1.2.0]: https://github.com/<owner>/<repo>/compare/v1.1.0...v1.2.0
```

## 10. Historical integrity

Never delete released versions, invent historical entries, change past dates, renumber
versions, restyle old entries or drop compatibility and security notes. Correct history
only with evidence, as a focused change with a stated reason, and never by rewriting
published Git history.

## 11. When to add an entry

Add entries for significant features, important fixes, user-visible behaviour changes,
breaking changes, security fixes, privacy changes, platform-support changes,
methodology changes and measured performance improvements. Routine formatting, minor
refactoring, test-only runs and ordinary documentation corrections usually need none.
Never put tool session records, conversation links or AI attribution in a changelog;
keep legitimate authorship and required attribution.

## 12. Verification

Before committing: behaviour, version, released/unreleased state, categories, platforms,
dates, compatibility, security and privacy claims, links, consistency with the README and
no private information; historical entries preserved; diff reviewed. After pushing:
the change is on the intended branch, CI checked, rendering and links checked, no
unintended tag or release. Fix mistakes with a follow-up commit.
