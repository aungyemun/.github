# General Writing Policy

## Language
- Clear, natural, professional English with correct grammar and terminology; one spelling
  convention per repository.
- Short, direct sentences; say things once.
- No promotional or exaggerated language, unqualified superlatives or vague claims
  ("improves performance") without specifics.
- No generic filler that restates headings or summarises what was just said.
- No emojis or decorative formatting in formal technical documentation unless the
  repository already uses them deliberately.

## Accuracy
- Document what exists now; label experimental, deprecated and planned items explicitly.
- Never invent features, tests, results, certifications, benchmarks, compatibility,
  versions, URLs, download links, contacts or dates.
- Verify versions, supported operating systems, commands, paths and output; mark anything
  unverified. Distinguish facts from assumptions and state limitations.
- Architecture and design documents describe the implemented design; proposals are
  labelled as proposals.

## Consistency
- Consistent product names, terminology, capitalisation and heading style (follow the
  repository's existing choice).
- Commands in fenced code blocks with a language tag; state the shell when it matters.
- Relative links inside the repository; check that they resolve.
- No contradictions or diverging duplicates across documents; keep one authoritative
  section and link to it.

## Readability
- Headings ordered by reader needs; short paragraphs; lists for steps; tables only for
  real comparisons; define terms on first use; keep documents as short as the content
  allows; put frequently needed information where it is easy to find.

## Maintenance
- Update documentation in the same change that alters behaviour.
- Remove outdated content only when it is genuinely outdated and the task allows it.
- Preserve legally and scientifically important text verbatim.
- Keep internal links accurate; avoid unrelated or purely stylistic rewrites.
