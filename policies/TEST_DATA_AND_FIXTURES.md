# Test Data and Fixtures

Engineering policy for test materials: choosing them, creating professional sample
files, synthetic and scientific data, fixture categories, expected outputs, storage,
provenance, licensing and privacy. Test strategy and execution are in
[TESTING](TESTING.md). Applications differ: create only the materials the tested feature
needs.

## 1. Before creating materials

1. Identify the feature and behaviour under test.
2. Inspect the existing fixtures and reuse them where they fit.
3. Decide whether new material is needed at all.
4. Choose the file formats the feature really handles.
5. Define the expected behaviour first (section 5).
6. Decide whether realistic presentation matters (rendering, layout, OCR, printing) or
   whether minimal synthetic content is enough.
7. Consider size, storage location, licensing and privacy (sections 6-7).

Never generate fixtures unrelated to the test.

## 2. Professional sample documents and images

When presentation matters, make samples that look like real material: PDF reports,
fillable forms, scanned pages, Excel workbooks, CSV datasets, PowerPoint slides, Word
documents, images, microscopy examples, charts, tables, database records. Use proper
typography, alignment, spacing and layout with realistic but synthetic content (invented
names, addresses and values that are clearly not real people or real results). Technical
validity comes first: the file must exercise the features under test (fonts and
encodings, form fields, embedded images, multi-page structure, Unicode, right-to-left
text, large tables) - appearance never replaces that.

## 3. Scientific test materials

Use technically correct formats - FASTQ, FASTA, GTF/GFF, SAM/BAM, count matrices, sample
metadata, statistical reference outputs, scientific images, reference database
metadata - small enough for routine tests (e.g. a few reads mapped to a short synthetic
contig). Record how each was produced (generator, seed, parameters, source subset and
its accession) ([SCIENTIFIC_PROVENANCE](SCIENTIFIC_PROVENANCE.md)). Never present synthetic
data as experimentally observed findings, and never use real patient or participant data
([PRIVACY](PRIVACY.md) section 3).

## 4. Fixture categories

Keep categories distinct and identifiable by name or location:
- **valid representative inputs**;
- **edge cases** (empty, minimal, maximal, Unicode, unusual but valid);
- **negative or malformed inputs** - clearly labelled as intentionally invalid (e.g. a
  `malformed/` folder or `bad_` prefix) so they are never used as valid benchmarks;
- **stress materials** (large or numerous files), usually generated on demand rather than
  stored;
- **golden or reference outputs**.

## 5. Expected results (test oracles)

Define what correct means before running: expected metadata, record counts, calculated
values (with tolerances justified by the method), file structures, UI behaviour, database
state, scientific outputs. Prefer independently established expectations (hand
calculation, a reference implementation, a published example, a previous validated
version) over output copied from the code under test. Never regenerate golden files just
because the implementation's output changed: first decide whether the change is
intended, explain it, and update the expectation only for an intended change.

## 6. Storage and provenance

| Kind | Where |
| --- | --- |
| Small fixtures needed by tests | tracked in the repository's test-data location |
| Large or bulky generated fixtures | generated by a script or test setup on demand; the generator is tracked, the output is not |
| Downloaded public fixtures | fetched by a documented step with a version-specific URL and checksum; cached outside Git |
| Restricted or confidential material | never in the repository; local, access-controlled, and only with authorization |

For each non-trivial fixture keep: source, generator and version, licence, test purpose,
checksum where useful and the expected results (a short README or manifest next to the
fixtures). Avoid duplicate copies of the same material. Never commit confidential or
oversized material without authorization ([REPOSITORY_HYGIENE](REPOSITORY_HYGIENE.md)
section 3).

## 7. Licensing and privacy

Use only material the project may redistribute: self-made synthetic content, public
domain, or openly licensed data whose licence permits inclusion (record it). Remove
metadata that identifies people or machines (author fields, GPS EXIF data, file paths in
document properties). Personal, confidential or research data never becomes a fixture
([PRIVACY](PRIVACY.md) sections 3 and 12).

## 8. Reproducibility

Generated fixtures are reproducible: fixed seeds, pinned generator versions and recorded
parameters, so that a regenerated fixture is identical or the difference is explained.
